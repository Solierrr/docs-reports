O web-app atende os requisitos descritos com evidência no GitHub

O que a disciplina pede e como este documento se organiza?

O que a disciplina pede

A disciplina de Desenvolvimento de Aplicações Dinâmicas pede uma aplicação web em React com TypeScript, organizada em componentes, serviços, rotas e recursos de acessibilidade. Há requisitos mínimos, que valem a nota 7,0, e requisitos extras.

O que o projeto entregou

A interface web do projeto é o repositório web-app, construído com Vite, React e TypeScript. A entrega web reúne também a biblioteca de componentes lib-web, a entrada de borda worker-failover, o portal público de documentos worker-docs e a interface de administração do QA web-sandbox. O código é organizado por funcionalidade, com serviços de API por domínio, tipos por domínio, estados de carregamento e erro, e um histórico de commits no padrão Conventional Commits. Este documento descreve os requisitos tratados e mostra, para cada um, onde o web-app o atende.

Como ler este documento

Cada requisito tem um identificador (M para mínimo e E para extra), o enunciado da disciplina, a descrição do que o projeto entrega e um ou dois links diretos. Todos os links apontam para a branch main e abrem o arquivo ou a pasta que comprova o requisito. Os requisitos aparecem em grupos por tema, na ordem em que o código é lido.

A base do web-app usa Vite, React e TypeScript, organizada por funcionalidade

Como o código está montado, dividido e tipado?

M1 Vite com React e TypeScript

Projeto criado com Vite e template React TypeScript; todos os arquivos de src/ em .ts ou .tsx, proibido .js e .jsx.

O web-app foi criado com Vite, React e TypeScript, como mostram as dependências do package.json. A pasta src/ não tem nenhum arquivo .js ou .jsx, e o ponto de entrada é o main.tsx.

  • package.json em web-app
  • main.tsx em web-app

M2 Organização de componentes e páginas

Componentes em src/components/ e páginas em src/pages/, cada um em pasta própria com index.tsx.

O projeto organiza o código por funcionalidade. Cada domínio do negócio tem uma pasta em src/features/ com suas páginas (pages/) e seus componentes (components/), e os componentes reutilizáveis ficam em src/lib/components/.

  • pasta src/features em web-app
  • pasta src/lib/components em web-app

M3 Componentes de responsabilidade única

Mínimo de 6 componentes com responsabilidade única.

O web-app tem dezenas de componentes reutilizáveis, cada um com uma função só. Entre eles estão a barra lateral (Sidebar), o gráfico (Chart), a seleção (Select), o menu de contexto (ContextMenu), os cartões de indicador e os componentes de feedback ao usuário.

  • Chart.tsx em web-app
  • pasta src/lib/components/ui em web-app

M4 Tipos TypeScript por domínio

Interfaces TypeScript para props e entidades do domínio em src/types/, por arquivo de domínio; proibido any.

Serviços, estado, efeitos, listas e rotas seguem padrões definidos

Como o web-app busca dados, guarda estado e navega entre páginas?

M5 Comunicação com a API em serviços

Toda comunicação com API isolada em src/services/, por recurso, com retorno Promise<Tipo> e try/catch; chaves e URLs em variáveis de ambiente.

A comunicação com a API fica em serviços por domínio, no padrão src/features/<domínio>/<domínio>.service.ts, com retorno tipado. O analytics.service.ts é um exemplo, e o company.postal.service.ts tem teste próprio. As URLs vêm de variáveis VITE_ listadas no .env.example, e o arquivo .env fica fora do versionamento pelo .gitignore.

  • analytics.service.ts em web-app
  • .env.example em web-app

M6 Estado local com useState

Estado local com useState, campos relacionados agrupados em um objeto; proibida mutação direta de arrays e objetos.

O formulário de cadastro de empresa, em CompanyOnboarding.tsx, usa useState e agrupa os campos de endereço em um único objeto de estado.

  • CompanyOnboarding.tsx em web-app

M7 useEffect com dependências

useEffect com array de dependências explícito e correto.

O ESLint do projeto ativa a configuração recomendada do plugin eslint-plugin-react-hooks, que aplica as regras dos hooks a todo o código. A página AnalyticsPage.tsx usa useEffect com o array de dependências declarado.

  • eslint.config.js em web-app
  • AnalyticsPage.tsx em web-app

M8 Listas com chave estável

Listas dinâmicas com key de identificador único; proibido key={index}.

O web-app informa o usuário, cuida da acessibilidade e mantém um histórico padronizado

Que cuidados de uso e de processo o projeto mostra?

M11 Acessibilidade

Acessibilidade mínima WCAG 2.1 AA, com botões, label e htmlFor, alt, contraste, role="alert", teclado e foco visível.

O projeto reúne recursos de acessibilidade em vários pontos. A pasta src/lib/shared/accessibility traz a geração de texto alternativo por IA para imagens. Mensagens de erro usam role="alert" em 36 arquivos, e o foco visível (focus-visible) aparece em 28 arquivos. Os componentes de feedback ficam em src/lib/components/feedback.

  • pasta src/lib/shared/accessibility em web-app
  • pasta src/lib/components/feedback em web-app

M12 Feedback de operações assíncronas

Feedback visual para operações assíncronas com três estados (carregando, sucesso, erro); proibido alert() e console.log como único tratamento.

A página de indicadores, AnalyticsPage.tsx, mostra um estado de carregamento enquanto busca os dados, uma mensagem de erro com role="alert" quando a busca falha e os dados quando ela termina. Dezenas de componentes usam estados de carregamento, apoiados pelos componentes de feedback do projeto.

  • AnalyticsPage.tsx em web-app

M14 Commits em Conventional Commits

Mínimo de 20 commits em Conventional Commits, cobrindo ao menos 4 semanas.

O histórico do web-app tem mais de 370 commits entre 02/06/2026 e 02/11/2026, e mais de 200 deles usam os prefixos feat, fix, refactor ou docs do Conventional Commits. O workflow pr-title-lint.yml recusa título de PR fora do padrão.

Os extras entregues cobrem contexto, hook com cancelamento e proteção contra XSS

Que recursos além do mínimo o web-app entrega?

E1 Context API

Context API com Provider dedicado, hook de consumo e tipagem; demonstrar o problema de prop drilling.

O contexto da empresa ativa, em ActiveContext.tsx, tem um Provider dedicado (ActiveContextProvider), uma interface tipada para o valor do contexto e um hook de consumo (useActiveContext).

  • ActiveContext.tsx em web-app

E3 Hook customizado com AbortController

Hook customizado com retorno tipado, loading, erro e cancelamento via AbortController.

O hook useMarketplaceCatalog, em marketplace.hooks.ts, é genérico e devolve os itens tipados, o estado de erro e uma função para tentar de novo. Enquanto a busca não termina, os itens ficam nulos e a interface mostra o esqueleto de carregamento. A busca é cancelada com AbortController quando o componente sai da tela.

  • marketplace.hooks.ts em web-app

E7 Proteção contra XSS

Proteção contra XSS, com dangerouslySetInnerHTML proibido para dados externos.

O código de src/ não usa dangerouslySetInnerHTML, então nenhum dado externo é inserido como HTML. O arquivo sanitization.utils.ts reúne a função de sanitização disponível para esse caso.

  • sanitization.utils.ts em web-app

Entregas adicionais

O que o projeto reúne nesta disciplina?

A entrega web inclui uma biblioteca de componentes publicada como pacote, com tokens de design e Storybook, um Worker na borda que roteia o idioma, reconhece a procura por caminhos de painéis e mostra uma página temporária quando a origem está indisponível, um portal público de documentos em três idiomas e uma interface de administração do QA com proxy autenticado do Swagger. No web-app, o Storybook tem mais de oitenta arquivos de story, a internacionalização cobre português, inglês e espanhol e as rotas são protegidas por guardas de acesso.

Link de exemplo, lib-web na branch main.
