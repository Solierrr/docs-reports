O que a disciplina pede

A disciplina de Desenvolvimento de Operações Ágeis pede práticas de entrega contínua, com revisão de código por pull request, infraestrutura em nuvem, contêineres e orquestração. Há requisitos mínimos, que valem a nota 7,0, e requisitos extras.

O que o projeto entregou

O projeto usa pull requests com regras de proteção da branch principal, publica a produção no Google Cloud em um cluster Kubernetes gerenciado por GitOps e empacota os serviços em imagens Docker. Os repositórios têm README, template de pull request e pipelines de build, testes e publicação de imagem. Este documento descreve cada requisito tratado e mostra onde ele está.

Como ler este documento

Cada requisito tem um identificador (M para mínimo e E para extra), o enunciado da disciplina, a descrição do que o projeto entrega e, quando há arquivo ou pasta que o comprova, um ou dois links diretos. Os links apontam para a branch main e abrem o arquivo ou a pasta que comprova o requisito. Quando o mesmo padrão existe em vários repositórios, o documento mostra um exemplo e cita os demais pelo nome.

Como o projeto revisa o código, onde ele roda e como é empacotado?

M1 Code review e pull request com aprovação

Aplicar Code Review e Pull Request juntamente com as aprovações.

Os rulesets de proteção de branch, guardados no docs-warehouse, exigem pull request, uma aprovação, revisão do responsável pelo código e merge por squash na branch padrão, além de revisão automática do Copilot. O api-core mostra o processo no dia a dia. Ele tem template de pull request, o arquivo CODEOWNERS com o revisor responsável e o workflow pr-title-lint.yml, que valida o título do PR a cada abertura.

  • pasta github/rulesets em docs-warehouse
  • CODEOWNERS em api-core

M2 Cloud como infraestrutura

Utilizar a Cloud como infraestrutura para hospedar o projeto.

A produção roda no Google Cloud. O Terraform do infra-platform descreve a rede, o cluster GKE, o NAT e o Argo CD, e o infra-gitops mantém o estado desejado do cluster.

  • modules/cluster/main.tf em infra-platform
  • README.md em infra-gitops

M3 Contêineres e orquestração

Utilizar tecnologia de container e orquestração (Docker e Kubernetes).

Os serviços são empacotados em imagens Docker, e mais de 15 repositórios têm Dockerfile, entre eles api-core, web-app e ai-assistant. A orquestração usa Kubernetes. O infra-gitops guarda os manifests de cada serviço (Deployment, Service e Ingress), uma aplicação do Argo CD por serviço e a aplicação raiz que as reúne.

  • Dockerfile em api-core
  • pasta services em infra-gitops

Os repositórios têm README completo e abrem pull requests com um template

Como o projeto documenta o código e padroniza as mudanças?

E1 README do projeto

Criar o README do projeto, completo.

O README do api-core aponta para a documentação em docs e flows, que inclui ARCHITECTURE.md, RUNNING.md e DEPLOY.md, com a arquitetura, a forma de rodar e a forma de implantar o serviço. O mesmo padrão de README aparece também em web-app, ai-assistant e infra-platform.

  • README.md em api-core
  • ARCHITECTURE.md em api-core

E2 Template de pull request

Definir Template de Pull Request e aplicar durante o desenvolvimento.

O template do api-core abre o pull request com as seções Objetivo, Alterações, Endpoints afetados, Banco de Dados, Como testar e Evidências. Cada pull request abre com esse roteiro. O arquivo pull_request_template.md existe também em web-app, ai-assistant, infra-platform e infra-gitops.

  • pull_request_template.md em api-core

O pipeline publica e implanta os serviços, e este documento cumpre a entrega

Como o código chega ao ambiente e como a disciplina é comprovada?

E3 Pipeline de implantação

Elaborar pipeline para implantação (GitHub Actions ou Jenkins).

O api-core roda os testes com cobertura a cada pull request e a cada push na main pelo workflow ci.yml, e publica a imagem do serviço pelo release.yml. Ele ainda tem versionamento e changelog automáticos (release-please.yml) e análise de qualidade (sonarqube.yml). Na implantação, o Argo CD sincroniza o cluster a partir da main do infra-gitops. O web-app publica o Storybook no GitHub Pages pelo workflow preview.yml.

  • ci.yml em api-core
  • pasta apps em infra-gitops

E4 Documento de entrega com link direto

Entrega, com documento de entregas descrevendo cada requisito, com link direto para o requisito.

Este documento é a entrega pedida. Ele descreve cada requisito tratado e traz, para cada um, um link direto para o arquivo ou a pasta que o comprova na branch main.
